이번 협의에서 결정하려는 것
==========================
사용자는 “방향은 맞는가? 이대로 E2E를 반복하면 언젠가 완성되는가?”라고 물었습니다.
이전 Pro 검토의 최소 수정안을 구현했지만 의미 오류가 다시 나타났습니다. 구현자는
“방향은 타당하나 같은 사건을 감독자가 계속 정정하며 재개하는 방식으로는 개선과 완성을
입증하기 어렵다”고 답했습니다. 이 답에도 반대할 부분이 있으면 분명히 지적해 주세요.

새 기능 목록보다 다음 세 가지를 결정하고 싶습니다.
1. 현재 하네스에서 유지·중단·단순화할 것.
2. 지침 불이행, 입력/상태 전달의 부담, 압축, 모델의 증거 해석 한계를 나눌 가장 작은 실험.
3. 언제 전체 E2E로 복귀하고, 언제 지침 추가를 멈추거나 접근을 바꿀지 판정할 기준.

요청한 것은 검토와 제안입니다. 모델/서비스 교체, 추가 호출, 운영 사건 수정의 승인이 아닙니다.
읽은 정확한 커밋·파일·함수를 적고 코드 사실, 전달받은 운영 관찰, 추론, 미실행 제안을 구분해 주세요.
실제 원문·사건·운영 설정·자격정보는 공개하지 않았습니다. 아래 관찰은 운영자 집계이며
공개 저장소에서 실제 사건의 결론 정답이나 원격 서버 상태를 재현할 수는 없습니다.

제품 목표와 책임 경계
====================
사용자의 목표는 정상으로 충분히 설명한 범위를 축약하고, 중요한 의심은 적극 추적하며,
로그가 부족해도 근거·가정·반론이 추적되는 가장 설명력 높은 판단을 내는 포렌식 에이전트입니다.
모든 것을 판단 불가로 미루는 답도 실패입니다. “유력”이라는 단어로 과잉 추론을 포장하는 것도 실패입니다.

단기 수용 목표 후보는 “사람이 검토할 수 있는 유용한 조사 초안”입니다. 이것은 구현자의 제안이지
사용자의 최종 제품 목표를 임의로 축소한 결정이 아닙니다. 무인 전문가 수준의 종결까지 어느 정도
검증이 필요한지, 둘을 어떤 사용자 경험과 품질 기준으로 구별할지 조언해 주세요.

- 판단·우선순위·경쟁 설명·다음 검사·종결은 모델이 선택합니다.
- 하네스는 원본 읽기 전용, 사건/권한 경계, 실제 반환, 참조/버전, 실행-평가 연결,
  충돌/재요청, 현재 판단의 수명과 전달을 보장합니다. 자연어 함의를 판정했다고 주장하지 않습니다.
- Hermes native loop/goal/session/도구/압축과 기존 사건 원장을 유지합니다.
- 경로/문자열/사건별 차단, 고정 점수나 근거 개수에 따른 확정 규칙은 만들지 않습니다.
- 두 번째 판단 장부·독자 실행기·반복 리뷰 모델·벡터 RAG는 필요성을 입증하기 전 도입하지 않습니다.
- 기존 사설 Ollama qwen3.8:latest를 유지합니다. 모델 교체는 자동 실행할 해결책이 아닙니다.

이전 Pro 검토 이후 실제 바꾼 것
==============================
아래는 이 커밋의 코드에서 확인할 수 있습니다. 작동 경로와 호환성에 잘못 연결된 부분이 없는지
독립적으로 검토해 주세요. “이전 제안을 구현했다고 적었으므로 올바르다”는 전제로 보지 마세요.

A. 검사 평가와 종합 판단
- test-only assess는 answer 없이 가능하며 국소 outcome을 큰 Question.assessment로 자동 승격하지 않습니다.
- 바뀐 종합 판단은 선택적인 question_update로 같은 저장 흐름에서 갱신합니다.
- 기존 flat 입력은 호환하되 종합 판단 최신성/재검토 필요를 구별합니다.
- 기존 노트 writer에서 현재 Claim 유지/대체/철회를 연결하고 과거 검사 이력은 보존합니다.
- fact/interpretation, 선택적 inference_strength(favored/plausible/unrated), assumptions를 연결했습니다.
  과거 adopted/supported에서 유력도를 자동 생성하지 않습니다.

B. 현재 상태의 전달
- current_judgment.py의 공통 파생 보기로 질문/Claim/Assessment의 현재 관계를 읽습니다.
- 턴 시작·압축·goal·보고에서 최신 판단, 한계, 다음 검사, 정정 상태와 참조를 제공합니다.
- 긴 판단 문장을 무작정 앞부분만 자르기보다 상세 조회 위치와 생략을 표시합니다.
- 현재에서 제외된 옛 정의의 보존 이력 수와 종결 색인을 제공합니다.
- 보고서 기본 제목과 조사 상태 문구를 중립화했습니다. 현재 선택된 결론과 과거 이력을 구분합니다.

C. 입력·근거 계약
- compact/legacy 입력 진단을 정리하고 reason/correction_reason의 서로 다른 위치를 문서와 맞췄습니다.
- metadata/exact_excerpt/full_field의 기술적 호환을 검사합니다.
- 검색 반환에 입력/출력 역할, 처리·건너뜀, coverage, cursor와 미측정 속성을 짧게 제시합니다.
  원문 반환과 source version은 보존합니다.
- 마지막 수정은 source 페이지의 버전 인자 오류에 실제 복구 경로를 안내하는 것입니다.
  source_id만으로 첫 조회 → source_ref.version 확인 → 그 source_version과 pointer로 페이지 조회.
  state의 snapshot_id와 혼동하지 않도록 했으며 stale 버전을 조용히 교체하지 않습니다.

D. 지침
- 원문 관측 → 실제 측정 범위 → 현실적 경쟁 설명 → 다음 판별 순서로 정리했습니다.
- 관리/조사처럼 보이는 활동의 성격과 승인·주체·악성 계열·성공 효과를 별개로 다룹니다.
- 날짜/수량을 인용 필드와 대조하고 파일명에서 본문 기간·소실 원인을 만들지 않도록 합니다.
- 내부 인자/버전 오류를 외부 자료 소실로 바꾸지 않도록 했습니다.
이 원칙 상당수는 이전에도 존재했습니다. 최근 지침 추가가 모델 행동에 효과 있다는 증거는 아직 없습니다.

- 마지막 회귀는 실제 Case.invoke 경로에서 잘못된 버전을 거절하고, 문서대로 첫 조회와 정확 페이지 조회를
  수행하여 원문을 회수하며, 원본/질문/평가를 바꾸지 않는지를 합성 사건으로 확인했습니다.
- 별도 모델 의미 benchmark, V0~V4 비교, 조건을 가린 사람 채점, 홀드아웃 E2E는 아직 실행하지 않았습니다.
- 테스트 일부는 judge/summary를 mock합니다. 통과는 모델 의미 정확성의 증거가 아닙니다.
- 이번 공개용 export에서 7개 모듈 134개가 통과했습니다: test_mission_native_tools, test_investigation_state,
  test_investigation_context, test_native_goal_evaluation, test_report_driven, test_reporting_pages, test_current_judgment.
  앞의 199/48개와 중복되며 독립 의미 시험으로 합산하지 않습니다.

최근 E2E에서 실제 본 것
=======================
같은 사건을 여러 차례 감독 중단·재개한 연속 관찰입니다. 독립 시행이나 수정 전후 통제 실험이 아닙니다.

개선된 동작:
1. 새 목록 도구 반환의 빈 allocated 엔트리를 선택 범위의 현재 관측으로 사용할 수 있었습니다.
   이전의 “건너뛴 본문 검색 무결과를 이름 부재로 변환”한 것과는 달랐습니다.
2. 답 정정 후 이전 채택 Claim이 superseded 이력으로 보존되는 실제 저장을 확인했습니다.
3. 압축 뒤 현재 revision·모델 판단이라는 출처 표시·보존 이력·보고서 상태가 복원됐습니다.
4. 새 노트 revision과 4개 보고서 파일이 생성됐습니다.
5. 마지막 native judge는 DONE이 아니라 blocked/pause를 선택했습니다. 허위 전체 완료라고 분류하지 않습니다.

남은 오류와 한계:
1. 인용한 인증 로그 페이지는 한 달의 여러 날짜인데 답에서 일부 일자를 다음 달의 날짜로 옮겼습니다.
   반환된 페이지 밖의 내용까지 본 것처럼 써서는 안 됩니다. 계정/IP/실제 날짜는 이 문서에서 생략했습니다.
2. 로그 디렉터리의 가장 이른 파일명을 보고 과거 로그가 “회전으로 소실됐다”고 확인 사실처럼 적었습니다.
   그 목록은 본문의 실제 날짜 범위나 소실 원인을 입증하지 않습니다.
3. 명령/검색 인자에 있는 위협 관련 문자열을 특정 계열의 과거 존재·제거 해석에 다시 사용했습니다.
   관리형 활동에서 승인된 내부 행위자까지 묶는 확장도 남았습니다. 뒤에 실제 귀속은 미정이라는 단서가
   있지만 앞선 강한 문장을 충분히 제한하는지 문제입니다. 유력한 활동 설명 자체를 금지하려는 것은 아닙니다.
4. 두 source 페이지에 source_version 대신 snapshot_id를 보냈습니다. 거부 뒤 원문 discovery를 하지 않고
   재인용이 불가능하다고 설명했습니다. 이것은 보존 원문의 부재가 아니라 복구 가능한 입력 실패였습니다.
5. 미평가 결과와 일부 로컬 자료가 남은 상태에서 “가치 있는 검사를 소진했고 나머지는 외부 자료가 필요”라고
   설명했습니다. native judge가 이를 받아 pause했습니다. 실제로 남은 모든 검사의 가치가 높다는 주장도 아닙니다.
   가능한 내부 복구를 시도/처분하지 않고 전역 외부 차단으로 묶은 것이 감독의 문제 제기입니다.
6. 질문 분리·구조화된 미션 평가가 충분히 정착했다는 증거는 없습니다. 큰 질문 하나와 legacy note 저장으로
   다시 빠지는 관찰이 있습니다. 노트 저장 성공과 새 assess 성공을 같은 지표로 세면 안 됩니다.

마지막 조치:
- native judge가 정지한 상태에서 감독자가 위 근거 불일치를 확인했고 일반 지침/오류 안내를 보완했습니다.
- 같은 사건을 재개했습니다. 모델의 실제 응답과 갱신된 스킬 3개의 반환을 확인했습니다.
- 모델은 날짜/소실 단정 오류를 인정했습니다. 이것은 새 노트·보고서의 정정 완료나 독립 추론 성공이 아닙니다.
- 감독자가 정확한 오답 위치와 근거를 알려준 재개입니다. 이후 성공하더라도 무개입 E2E 성공으로 집계할 수 없습니다.
- 현재 E2E는 진행 중입니다. 이번 검토서 작성 때문에 추가로 중단·초기화하지 않았습니다.

문맥 압축과 서버를 분리해 봐 주세요
=================================
과거 원격 서버의 실효 context 4,096 문제는 운영자가 65,536으로 수정했다고 인계했고, 클라이언트에서도
제한된 긴 입력/도구 표식 검사를 통과했습니다. 65,536 전체 구간 의미 정확성이나 영구 무잘림을 검증한 것은 아닙니다.

최근에는 요약 호출이 호스트의 약 300초 대기 경계에서 취소된 관찰이 있어 native 설정만 조정했습니다.
- context_length 65,536, threshold_tokens 40,000
- auxiliary.compression.timeout 600초, compression.context_timeout_seconds 600초
- 일반 context_total_ceiling_seconds 900초 (native over-window 경로의 별도 600초 상한은 유지)
- 모델/템플릿/서버 주소는 변경하지 않았습니다. 운영 자격정보/주소는 공개하지 않습니다.

설정 변경 이후 관측 표본:
- 요약 호출이 약 249초, 346초, 333초, 마지막 재개에서 454초에 완료됐습니다.
- 마지막 재개: 요약 입력 15,175 / 출력 11,198 토큰, 후속 주 모델 입력 37,970 / 출력 4,298 토큰,
  주 모델 약 395초. 스킬 세 개를 읽은 뒤 다시 native 압축을 시작했습니다.
- 출력 토큰은 provider가 보고한 사용량이며, 모두 사용자에게 보이는 요약 본문이라고 해석하지 마세요.
- 이 표본은 timeout 회복과 실제 진행의 증거입니다. 비용 개선이나 문맥 의미 보존의 정답률은 아닙니다.

중요한 가설: 너무 큰 스킬/도구 schema/보존 tail/요약이 유효 문맥을 차지하여 압축이 잦을 수 있습니다.
반면 이를 병목의 확정 원인으로 볼 계측은 아직 부족합니다. 임계값을 더 낮추거나 대기 시간을 더 늘리는
방식만 반복하지 않으려 합니다. 기존 Hermes의 summary 입력/출력 예산, 보호 tail, projection, trigger를
실제 코드로 확인하고 필요한 계측을 제안해 주세요. template와 init 기본값의 차이도 발견하면 지적해 주세요.

핵심 질문 — 우선순위대로 답해주세요
==================================
1. 개발 방향과 중단 기준
   현재 구조는 이 모델이 이용하기에 지나치게 복잡한가요? 무엇을 유지하고 어떤 노출 입력/절차를 줄일까요?
   공개 코드에서 확인되는 결함과 모델이 사용하지 않는 계약을 나눠 주세요. 독립 질문 분리는 누가 언제
   수행해야 하며 모든 원문/파일마다 미션을 만드는 부담을 피할 수 있나요?

2. 다음 단 하나의 실험
   앞으로 기능을 더 만들기 전에 무엇을 한 번 비교해야 가장 많은 불확실성이 줄어드나요?
   짧은 핵심 원문 직접 제공(진단), native 도구 경유, 상태 갱신+압축 후 재개 중 최소 비교군을 고르고,
   고정할 값·예산·중단 조건·관측 지표를 실행 가능한 수준으로 제안해 주세요.
   모델 digest/양자화/서버 버전/sampling/실효 context가 아직 실험 조건표로 고정되지 않았다는 점도 고려해 주세요.

3. 지침을 그만 추가할 시점
   같은 짧은 원문에서도 검색 인자를 검출 결과로 읽거나 원문 날짜를 바꾸면 어떤 결과를 모델 한계의
   증거로 인정할까요? 한 번 실패로 단정하지도, 무한히 프롬프트를 보강하지도 않는 작은 반복 설계를 원합니다.
   도구 출력이 명확한데 해석이 틀린 경우와, 복구 경로/문맥이 없어 틀린 경우의 구별 기준을 제시해 주세요.

4. 완성의 정의
   사람 검토용 초안의 출하 기준과, 감독자 개입 없는 종합 조사 완료의 기준을 따로 제시해 주세요.
   과잉 확정·부당한 유력·과도한 보류·중요 단서 누락·부당한 차단/완료·불필요한 지속을 함께 평가해야 합니다.
   작은 고정 세트의 위반 0을 실전 오류 0으로 해석하지 않으면서도 go/no-go를 결정할 방법이 필요합니다.
   핵심 오류를 비용 감소로 상쇄하는 단일 종합 점수는 피하세요.

5. E2E의 검증 오염
   지금 실행은 감독자가 오류 위치와 수정 방향을 여러 번 알려준 사건입니다. 무엇을 회복 시험으로 인정하고
   무엇은 독립 평가에서 제외할까요? 기존 기록을 보존한 채 합성 개발군/홀드아웃/새 E2E를 구분하는 최소 설계는?
   초기화해서 같은 사건을 다시 돌리는 것이 왜 충분하거나 부족한지도 설명해 주세요.

6. 압축 비용과 의미 복원
   어떤 한 가지 계측/설정 또는 작은 입력 축소를 먼저 시험해야 하나요? 기존 native 구조를 유지해
   system/schema/skills/tail/summary/projection의 비용과 재압축 주기를 분리하는 방법을 원합니다.
   timeout 완화와 의미 오류 개선을 같은 성공으로 세지 마세요.

7. 감독 개입과 다음 3단계
   실제 중대한 오류는 안전하게 중단·정정해야 하지만 잦은 감독 개입이 평가를 오염시킵니다.
   개발 중 복구와 무개입 평가의 중단/재개 규칙을 분리해 주세요. 현재 실제 E2E를 계속할지,
   안전하게 보류한 뒤 짧은 평가를 먼저 할지 권고하고 그 선택이 틀렸음을 보여 줄 조건도 적어 주세요.
   세 단계 이내로 작업, 완료 기준, 실패하면 바꿀 접근, 대략의 호출 예산을 제시해 주세요.
