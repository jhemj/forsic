작성일: 2026-10-07
저장소: https://github.com/jhemj/forsic

검토 요청
=========
저장소 코드를 실제로 읽고, 기존 Hermes 구조를 최대한 활용하는 최소 개선안을
제안해 주세요. 이 문서의 진단도 가설과 관찰을 구별해 검증해 주세요.
파일에 접근할 수 없으면 그 한계를 먼저 밝히고 읽은 것처럼 답하지 마세요.
관찰된 실패에 대한 단순한 지침 추가보다, 에이전트가 조사 상태를 유지하고
근거를 되찾고 완료를 판단하는 경로의 결함을 찾아 주세요.

제품과 제약
===========
Forsic은 증거 경로로 사건을 정의하고 사건 안에서 대화를 묶는 로컬 포렌식 도구다.
고정 Hermes commit bafb42b431fca313471958fdf77f9c30e455f86b의 native 대화 루프,
도구 실행, goal, 중단·재개, 세션, 압축을 재사용한다. 모델은 기존 사설 Ollama의
qwen3.8:latest이고 문맥 설정은 65,536 tokens다. 모델 교체가 선행 조건인 안은
별도 대안으로만 설명해 달라. 공개 저장소에는 실제 사건·운영 설정이 없다.

지켜야 할 원칙:
- 별도 조사 루프, 독자 goal 스케줄러, 두 번째 세션 DB, 자체 압축기를 만들지 않는다.
- 특정 경로·문자열·정황 개수로 정상/악성을 결정하거나 자동 판정을 강제하지 않는다.
- 원본 읽기 전용, 사건 격리, 참조·버전·반환 범위의 기계적 검증은 유지한다.
- 정상으로 충분히 설명된 범위는 근거·재검토 조건을 남기고 활성 문맥에서 축약한다.
- 의심이 크거나 판단에 영향이 큰 항목은 불확실해도 적극 추적한다.
- 로그가 사라졌더라도 독립 정황을 비교해 가장 유력한 설명을 제시할 수 있어야 한다.
  관측되지 않은 파일 형식·삭제 행위·명령 성공·행위자·시각을 사실로 채우면 안 된다.
- 신뢰도와 조사 완료는 별개다. 모든 불확실성의 해소를 완료 조건으로 삼지 않는다.
- 실제 자료·토큰·원문을 새 외부 서비스에 전송하거나 새 모델 호출을 추가하지 않는다.
- 개발 지침은 루트 AGENTS.md, 조사 지침은 config/AGENTS.md와 skills에 둔다.
  루트 .hermes.md가 개발 지침의 조사 문맥 유입을 막는다.

현재 실패의 관찰 — 실제 사건 식별자·내용은 제외
==============================================
새로 초기화한 한 로컬 E2E를 감독하면서 아래 현상을 관찰했다. 집계는 한 실행의
진단이며 벤치마크나 일반 성능 추정이 아니다. 원본 자료는 공개하지 않았다.

1. 모델 응답 31회, 도구 반환 137개를 거쳐 보고서 4개를 만들고 완료를 선언했다.
   최종 노트는 1개였고 report state의 missions/tests/assessments는 모두 0이었다.
   스스로 중요하다고 적은, 이미 접근 가능한 로컬 검사도 수행하지 않고 남겼다.
2. 찾기 실패와 빈 디렉터리 조회를 근거로 '파일이 이미 삭제됐다'고 단정했다.
   동일한 유형의 다른 오해로, 제한된 감사 결과를 넓은 정상 기준선으로 해석하고
   연도 없는 로그에 특정 연도를 붙였다. 유효한 의심 단서 자체는 존재했다.
3. 최종 노트에 적힌 근거 목록이 핵심 주장에 사용한 본문 반환과 일치하지 않았다.
   참조 ID의 존재 검사는 통과해도 그 내용이 주장을 지지한다는 보장은 없었다.
4. 보고서 자체는 partial/draft/not_reviewed를 표시했지만 대화와 native goal은
   종합 조사 완료로 처리했다. 보고서 파일 생성과 조사 완료가 혼동됐다.
5. 압축 보조 호출 7회 중 2회가 300초 제한으로 취소됐다. 동일 원문 구간을 여러 번
   조회했다. 1개의 큰 노트로 끝났으므로 범위별 종결과 재사용이 정착됐다고 보기 어렵다.
6. 최초 단정 직전의 도구 반환은 삭제 이력이 입증되지 않았다고 명시했다.
   삭제 단정은 일반 assistant 응답에서 먼저 나타났고, 이후 압축 요약이 이를
   재서술하면서 일부를 도구 관측처럼 묶었다. 압축이 최초 오류의 원인이라는
   증거는 없다. 기존 오류의 재유통과 출처 구분 약화는 관찰됐다.

위 문제를 막는 일반 지침은 이미 있었다. 추가 지침 초안은 배포하지 않았다.
해당 E2E는 감독자가 native goal을 일시 정지했다. 이 문서를 구현 완료나
재개 검증, 의미 정확성 통과의 증거로 사용하지 말아 달라.

코드에서 확인한 현재 구조
========================
아래 설명의 정확성과 빠뜨린 경로가 있는지도 검토해 달라.

- forsic_plugin/report_driven/contracts.py
  Question/Hypothesis/Test/Gap/Mission/Assessment가 이미 있다. Question에는
  scoped_closed, blocked_*, budget_deferred 등이 정의된다. Mission은 30여 필드다.
- forsic_plugin/report_driven/host.py
  mission은 draft 저장만 허용한다. assess는 mission=partial, question=open,
  gap=assessed_unresolved로 기록한다. 노트의 answered도 열린 질문으로 투영한다.
  따라서 현재 계약은 보고용 제안에 가까우며 범위 종결·재개의 실제 경로가 부족하다.
- forsic_plugin/__init__.py
  reporting(state/gaps/source/mission/assess/review/render 등)을 등록한다.
  before_turn은 정적 조사 지침과 사건 정보를 넣지만 작은 활성 미션 상태를 넣지 않는다.
- forsic_plugin/notes.py
  list는 작은 색인, get은 최신 노트, save는 작은 영수증을 모델에 반환한다.
  상세 기록·수정 이력은 유지한다. 색인·저장 성공을 의미 검증으로 취급하지 않는다.
- forsic_plugin/report_driven/model_pages.py
  정확한 source/version/pointer의 UTF-8 구간 재조회가 있다. 모든 원문을 매번
  다시 수집할 필요는 없다. 현재 벡터 RAG를 추가한 상태는 아니다.
- upstream/hermes/tools/todo_tool.py 및 agent/conversation_compression.py
  native todo_list와 압축 뒤 활성 항목 재주입이 있다. 현재 조사 toolset은
  forsic만 노출하므로 모델에 todo_list가 제공되지 않는다.
- upstream/hermes/hermes_cli/goals.py
  judge_goal은 마지막 assistant 응답과 goal/contract/subgoals/background 정보로
  판단한다. 사건 원장·미션·도구 반환을 직접 조회하지 않는다. 이번 계약은 980자,
  마지막 응답은 2,337자로 각각 2,500/4,000자 제한 아래여서 잘림이 원인은 아니다.
  evaluate_after_turn에는 judge 이전 native gate 경로가 있으나 해당 실행은 gates=[]다.
- upstream/hermes/agent/context_compressor.py
  기존 압축기에 관측/해석/정정/근거 구분을 보존하는 지침을 추가한 유지 패치가 있다.
  별도 압축기나 분석 모델을 만들지는 않았다. 효과가 충분하다고 입증되지는 않았다.

검토 중인 방향 — 확정안 아님
===========================
A. 기존 사건 원장을 조사 상태의 단일 기준으로 삼는다.
   모델은 질문, 최선의 설명, 중요한 반론, 다음 판별 검사, 종결 이유·범위·재개
   조건을 짧게 작성한다. ID·버전·사건 연결 등 계산 가능한 필드는 호스트가 채운다.
   기존 Mission 전체 스키마를 매번 직접 작성하는 부담을 줄인다.
B. 상태에 열린 조사, 실행 중, 범위 종결, 자료/도구 차단, 예산 보류를 구별한다.
   결과가 반환된 것과 평가가 끝난 것, 질문이 종결된 것은 별개다.
   의미 판단은 에이전트가 하고 호스트는 유효한 참조와 변경 이력을 보존한다.
C. 압축 후에는 활성 질문·미션 ID·다음 검사만 작은 문맥으로 복원한다.
   native Todo를 원장의 작업용 색인으로 쓸지, 기존 hook에서 원장의 작은 투영을
   제공할지 비교한다. 모델이 독립 장부 두 개를 동기화하게 만들지 않는다.
D. 완료 판단에는 최신 조사 상태를 전달한다. native gate를 쓰더라도 참조·버전,
   미처리 항목의 상태·보류 이유 등 기계적 정합성만 검사한다. 모든 gap 해소,
   미션 N개 생성, 특정 악성 결론을 필수로 만들지 않는다. 종결 경로부터 구현하지
   않고 open gap 차단만 붙이면 영원히 끝나지 않을 수 있다.
E. RAG는 필요한 원문을 찾는 보조 수단으로 본다. 먼저 기존 정확 참조 조회를
   활용하고, 검색이 실제 병목일 때 사건 내부 원문 검색/인덱스를 검토한다.
   과거 분석 노트를 사실로 검색해 재주입하는 방식은 오류를 강화할 수 있다.

구체적으로 답해 줄 질문
======================
1. 실패 원인을 지침 불이행, 상태 관리, 도구 인터페이스 부담, 압축, 종료 판단으로
   나누어 우선순위를 정해 달라. 코드 근거와 아직 검증되지 않은 추정을 구별해 달라.
2. 기존 미션 구조를 최소한으로 완성하는 수정안은 무엇인가? 먼저 제거하거나
   단순화할 부분도 지적해 달라. 대규모 스키마/상태 기계를 추가하지 말아 달라.
3. native Todo와 사건 미션은 어떻게 연결해야 단일 기준을 유지하는가?
   여러 대화, 압축 후 재개, 취소/재시도/충돌에서 중복·누락을 어떻게 방지하는가?
4. 원문 근거를 직접 관측과 추론으로 구분하고 잘못된 인용을 줄이되, 확정 집착이나
   검토 무한 반복을 피하려면 어떤 계약과 소규모 검토 시점이 필요한가?
5. 완료 judge에 어떤 작은 상태를 전달해야 하는가? 기존 plugin hook/native gate로
   충분한지 실제 호출 경로로 설명해 달라. 새 loop 없이 가능한 최소 upstream
   변경이 필요하면 정확한 이유와 경계를 제시해 달라.
6. RAG를 지금 도입할 가치가 있는가? 정확 참조 재조회, 키워드 인덱스, 벡터 검색을
   비교하고, 사건 격리·출처·버전·검색 범위·무검색 결과의 한계를 어떻게 보존할지
   설명해 달라. 새 외부 임베딩 전송 없이 가능한 범위를 우선해 달라.
7. 정상 범위 종결로 문맥을 절약하면서 중요한 새 반증에는 다시 열리게 하려면?
   데이터 부족 상태를 정상이나 완료로 세탁하지 않는 방식을 설명해 달라.
8. 실제 모델 한계가 주원인이라면 이 구조로 개선 가능한 부분과 해결 못할 부분을
   구별해 달라. '모델을 바꾸면 된다'나 '프롬프트를 더 길게 쓰면 된다'로 끝내지 말라.

원하는 답변 형식
===============
- 결론과 우선순위, 현재 코드 경로에 연결된 이유.
- 지금 할 최소 변경안과 보류할 확장안. 파일별 변경 목적과 호환성 위험.
- 모델이 결정할 것 / 하네스가 검증할 것 / 원문 저장소가 보장할 것의 경계.
- native 구조와 단일 기준을 유지하는 상태 흐름 및 압축·재개 흐름.
- 반증 가능한 검증 계획. 테스트 통과와 실제 조사 의미 정확성 검증을 분리.

합성 평가에는 정상 잡음 속 의심 추적, 정상 종결 후 반증, 로그 결손이 있는
침해 정황, 명령만 있고 성공 불명, 상충 근거, 참조 버전 변경, 압축 후 재개,
부분 보고서와 조사 완료의 구분을 포함해 달라. 특정 표현 포함 여부나 호출 수
감소만으로 성공 판정하지 말고, 중요한 조사 누락·근거 일치·중복·문맥 비용·
판단 수정 여부를 함께 보라. 검토와 제안만 요청하며 실제 사건 재실행이나
외부 전송을 이 문서로 승인하는 것은 아니다.
