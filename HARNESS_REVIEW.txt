0. 이번 요청의 핵심
===================
당신이 공개 코드와 최신 관련 프로젝트를 조사하고, 구현에 바로 착수할 수 있는 완결된 설계·작업지시서를 작성해 주세요.
이 문서를 전달한 Codex에게 외부 하네스 비교 조사는 맡기지 않았습니다. 아래는 현재 구현의 설명과 설계 질문이며,
비교 후보들의 기능이나 우수성을 이미 검증했다는 뜻이 아닙니다. 후보 조사와 사실 확인은 이번 Pro 검토의 일입니다.

사용자의 목표는 다음과 같습니다.
“기본 에이전트가 자료를 읽고 의심을 추적하며 오류를 고치는 자연스러운 흐름을 유지하면서,
원본 보호·정확한 근거·전문 분석 도구·가설 검토·효율·보고 품질을 갖춘 포렌식 전문 에이전트.”

개별 입력 오류 한 건을 고치는 권고에서 끝내지 마세요. 접수 → 탐색/읽기 → 가설 비교 → 근거 선택과 판단 갱신 →
오류 복구 → 문맥 압축/재개 → 범위 종결 → 유용한 보고까지 전체 흐름을 설계해 주세요.
기존 구현을 유지해야 한다는 선입견 없이 불필요한 레거시·중복 상태·과도한 필수 절차를 제거 대상으로 검토하세요.
반대로 안전장치 삭제, 검증 완화, 도구 수 감소만으로 개선이라고 판단하지 마세요.

현재 AGENTS.md의 Hermes native 유지 원칙은 현행 운영·구현의 기준입니다. 이번 설계 검토에서는 사용자의 최신 요청에 따라
Hermes 유지/확장, 다른 검증된 하네스로의 이관, 작은 어댑터로 포렌식 기능을 분리하는 방안을 모두 비교할 수 있습니다.
Hermes 보존도 교체도 정답으로 미리 정하지 마세요. 선택 근거·비용·위험·전환 조건을 제시해 주세요.
설계의 선택지를 여는 것과 실제 운영 엔진·모델·권한을 지금 바꾸는 것은 별개입니다.

1. 자료의 범위와 답변의 증거 수준
================================
공개 소스, 유지 패치, 합성 fixture와 회귀검사를 제공합니다. 실제 사건 증거·원문 대화·운영 로그·보고서·설정·주소·
인증정보·실제 경로·사건/세션 식별자는 공개하지 않습니다. 아래 운영 설명은 익명화한 운영자 관측입니다.
공개 코드로 실제 사건의 정답이나 제공자의 원시 모델 생성을 재현할 수 있다고 전제하지 마세요.

답변에서 다음을 명확히 구분해 주세요.
- 직접 읽은 코드/공식 문서에서 확인한 사실
- 운영자가 전달한 관측
- 근거에 기반한 원인 가설 및 반론
- 아직 구현하거나 실행하지 않은 설계·실험 제안

저장소나 첨부 코드를 읽지 못하면 먼저 밝히고, 읽은 것처럼 답하지 마세요. 추가 자료가 필요하면 민감 원문 대신
어떤 함수·합성 재현·익명 집계가 필요한지 지정하세요. 인용은 고정 커밋의 파일·함수·관련 위치로 연결해 주세요.
현재 main은 바뀔 수 있으므로 조사 중간에 서로 다른 스냅샷을 섞지 마세요.

2. 제품에서 지켜야 할 것과 모델에게 맡길 것
==========================================
프로그램의 책임:
- 원본 읽기 전용, 사건·세션·권한 경계, 증거 속 명령/주소/지시문을 데이터로 취급하는 실행 환경.
- 실제 실행 시도·시작·반환·취소·실패의 기록. 불확실한 실행을 성공이나 미실행으로 바꾸지 않기.
- 보존 원문과 표시된 범위, 정확한 출처·버전·좌표, 이어읽기·검색 범위·부분 반환의 보존.
- 실제 선택과 충돌을 보존하는 저장, 중복 쓰기/실행 제어, 명시적 정정·철회 이력.
- 사설/민감 자료의 외부 전송을 승인 범위 안에서 통제하기.

에이전트의 책임:
- 어떤 자료와 가설을 먼저 볼지, 무엇이 중요한 반론인지, 어떤 설명이 가장 유력한지 판단하기.
- 직접 증거가 없더라도 독립 정황·출처·가정·경쟁 설명을 비교해 유용한 추론을 하기.
- 추가 검사의 가치와 비용을 평가하고, 불확실성을 남기면서도 합리적인 범위 종결을 하기.
- 정상으로 설명된 범위는 정리하고, 중요한 의심을 추적하며 질문에 답하기.

불확실성은 허용해야 합니다. 모든 연결의 직접 입증, 모든 파일 검사, 모든 상상 가능한 대안 소진을 요구하지 않습니다.
다만 “해석/추정” 표지는 잘못된 관측 사실을 정당화하지 않습니다. 검색 명령은 검색 결과가 아니고, 명령 기록은 실행 성공이나
행위자 귀속과 다르며, 부분 검색 0건은 시스템 전체의 부재가 아닙니다. 정상과 침해 어느 결론도 미리 유도하지 않습니다.

내부 ID·버전·바이트 좌표를 모델이 매번 다시 조립할 필요는 줄여야 합니다. 이미 명시적으로 선택된 대상에 대한 기계적 복원과,
프로그램이 최신 경로·미션·근거를 몰래 골라주는 것은 구분하세요. 충돌·사건 경계·정확 인용 검증은 보존해야 합니다.

3. 현재 코드에 이미 있는 것
===========================
현재 Forsic은 Hermes native 플러그인입니다. 별도의 모델 클라이언트나 조사 실행 루프를 새로 만들지 않았습니다.
대화·goal·도구 실행·세션·압축은 native 흐름에 연결하고, Forsic이 사건 접수·증거 접근·조사 상태·스킬·보고를 제공합니다.
아래가 실제로 남아 있는지 코드를 확인하고, 이미 구현된 기능을 새 권고로 중복 제안하지 마세요.

- 기본 분석은 미션 없이 직접 읽기/검색 → 명시적 인용 선택 → forsic_question의 현재 답/판단으로 진행할 수 있습니다.
- 미션은 필요한 사전 판별 검사의 계획입니다. 선택적 forsic_assess는 한 호출로 평가하며 별도 준비 영수증을 요구하지 않습니다.
- C2는 실제 읽기 반환에 제시된 보존 필드를 선택하고, C1은 보존 source 조회에서 선택합니다. 정확 버전/좌표는 프로그램이 복원합니다.
- 현재 답은 기존 노트 단일 writer에 저장하고, observation/claim을 연결합니다. 가짜 미션/test/assessment를 만들지 않습니다.
- 과거 노트는 조회 경로로 남고, 구형 보고/질문 생성/사후 미션/평가 준비의 일부 도구는 native 목록에서 제거됐습니다.
- 비교 투영을 native 반복 감지에 연결하여 reason·영수증 ID 변동과 실제 본문/페이지 변화를 구별합니다.
- 보존 목록 참조와 명시적 멤버 번호로 archive 읽기 대상을 복원합니다. metadata_checked는 암호학적 내용 동일성 증명이 아닙니다.
- 검색/상태/원문은 제한된 페이지와 이어읽기 참조를 제공하고, 압축에는 현재 조사 상태의 작은 투영을 연결합니다.
- 실제 읽기/검색/바이트 미리보기의 취득 성격과 범위를 observation/현재 판단으로 전달하는 변경이 들어 있습니다.
- 실제 도구 실행·실패·가드레일 결과가 native 턴 정리와 문맥 축약에서 사라지거나 새 결론으로 둔갑하지 않도록 유지 패치가 있습니다.
- 최근 변경은 공백 처분의 모델 스키마와 저장 검증을 일치시키고, 종결 시 빠진 공백을 정확히 안내합니다.
  native block/halt 후에는 관련 active goal의 pause를 저장하여 중단 상태를 일치시킵니다.

남은 중요한 설계 질문:
현재 forsic_question의 judgment에는 근거/반대 근거·주장 유형·추론 강도·추론 요약·가정·한계가 있습니다.
질문에는 별도로 answer·work_state·assessment·priority·공백 처분·재개 조건·revision·operation_id 등이 있습니다.
모두 같은 의미나 의무 필드는 아니지만, 모델이 분석하면서 이 계약을 동시에 관리해야 합니다.
최근 스키마 일치 수정은 복구에 도움을 주는 계약 수정이며, 관리 부담 자체를 크게 줄였다는 증거는 아닙니다.
이 중 필요한 분석 표현, 프로그램이 맡을 메타데이터, 중복된 절차를 구체적으로 나눠 주세요.

4. 운영 관측과 현재 검증의 한계
==============================
익명화한 운영자 관측:
- 직접 읽기와 검색은 진행됐고, 원문에 연결된 질문/claim/observation 저장까지 도달한 실행도 있습니다.
- 단일 인자 오류를 고치거나, 읽을 수 없는 대상에서 다른 명시적 자료로 전환한 사례가 있습니다.
- 반면 판단 저장/종결의 입력 요구와 페이지로 나뉜 공백 목록을 처리하다 반복 실패하여 native가 중단한 사례도 있습니다.
- 일부 초안/작업 중 판단에는 명령과 출력, 시각과 실행 순서, 부분 읽기와 전체 부재를 과도하게 연결한 표현이 있었습니다.
  저장 거절 초안·현재 채택된 판단·최종 전달은 구분해야 하며, 모두 최종 보고서 오류로 취급하면 안 됩니다.
- 감독자가 기술적 결함을 고쳐 배포하고 빈 대화로 같은 사건을 다시 시작했습니다. 원본·원장·출처·보고서는 보존했습니다.
  빈 대화는 독립 신규 사건 시험이 아닙니다. 운영자의 패치/재시작을 제품의 자율 복구 성공으로 집계하지 않습니다.
- 최신 개선 후 실제 모델/도구 반환과 본문 읽기는 확인됐습니다. 최종 조사 정확성, 끝까지의 자율 복구, 보고 품질은 검증 중입니다.

현재 코드 스냅샷에 대한 오프라인 검사: 제품 362개 + 관련 native 30개, 중복 제외 392개 통과.
관련 없는 HTTP/ASGI 검사 1개는 제외됐으며, 전체 upstream 테스트 통과를 뜻하지 않습니다.
모델 호출 없는 합성/계약 검사입니다. 실제 조사 능력·속도 개선·패치 단독 인과의 증거가 아닙니다.

진단 경계도 유지하세요. pre_sdk_merged_body는 실제 HTTP 캡처가 아니며, accumulated_before_repair는 SDK 스트림 누적 후
복구 전 값입니다. 제공자 원시 생성은 미관측입니다. submitted_tool/submitted_arguments와 canonical 원장 입력의
의도된 변환을 구분하고, 필드 누락 원인을 모델 또는 전달 계층 하나로 단정하지 마세요.

각 프로젝트에 대해 “좋다/유명하다” 대신 아래를 표로 제시해 주세요.

- 작은 통합 경계, 반례, 오프라인 회귀, 롤백 방법.

특히 비교할 메커니즘:
자연스러운 도구 선택과 피드백, 오류 분류/수정/대안 전환, 반복/무진전 감지, 장기 세션과 중단·재개,
필요할 때 불러오는 도구/스킬/문맥, 결과 탐색과 상세 재조회, 플러그인 권한/격리, 원문과 요약의 연결,
취소·불확실 실행·중복 실행 관리, 작업 상태의 보존, 행동 평가와 관측 가능성.
ARTEX의 침투 실행이나 worker pool을 그대로 포렌식 권한에 가져오지 마세요. 설계 목적 차이를 검토하세요.
플러그인/스킬의 도입은 증거 실행·외부 전송·임의 설치 권한의 확대로 이어져서는 안 됩니다.

6. 반드시 답해야 할 설계 질문
============================
Q1. 목표 아키텍처와 엔진 선택
현재 구조를 먼저 한 장으로 설명한 뒤 권장 구조를 제시하세요. 실행 엔진, 포렌식 도구, 증거/출처 저장,
현재 판단, 문맥/스킬, 보고/UI, 운영 감독의 책임과 데이터 흐름을 명확히 하세요.
Hermes 유지+단순화 / 다른 기존 하네스로 이관 / 포렌식 도메인과 얇은 native 어댑터 분리를 비교하고 하나를 권고하세요.
판단에 부족한 증거와 권고를 뒤집을 조건도 쓰세요. 불필요한 범용 플랫폼이나 중복 실행기/판단 장부를 만들지 마세요.

Q2. 모델이 보는 조사 도구의 최소 계약
“읽고 이해하기, 추가 근거 찾기, 현재 답 고치기, 근거를 붙여 보고하기”가 직접적인 행동이 되게 설계하세요.
현재 exposed 필드와 호출 순서를 분석하여 유지/숨김/통합/제거 대상을 명시하세요.
원문 선택·판단·반론은 모델에게 남기고, 명시적으로 선택한 대상의 좌표·버전·재시도 식별자는 프로그램으로 옮길 수 있는지
검토하세요. 단순히 프롬프트에서 필드를 숨기거나 최신 레코드를 자동 선택하지 말고 안전한 인터페이스를 제시하세요.
유효 호출, 오류 반환, 수정 호출을 작은 합성 JSON으로 보여 주고 현재 경로와 필요한 호출/관리 입력 수를 비교하세요.

Q3. 미션·평가·질문·공백 구조의 존폐
현재 미션/Assessment/Claim/Observation/Note/Question/Gap 중 canonical 원장, 파생 뷰, 모델 입력을 구분하세요.
중복 구조와 레거시 호환 경로가 실제로 조사 흐름을 복잡하게 하는지 코드로 확인하세요.
일반 읽기마다 계획·평가를 요구하지 않으면서 사전 판별 검사가 유용한 경우만 선택적으로 보존할 방법을 정하세요.
공백을 빠짐없이 “처리”하는 행정 절차와 중요한 누락을 숨기지 않는 분석 의무를 어떻게 분리할지 답하세요.
한계·범위 종결·재개 조건의 중복 입력을 줄이면서 각 의미와 이력을 보존하는 방안을 제시하세요.

Q4. 포렌식 원문·인용·취득 범위의 최소 기반
읽기 반환, 목록/메타데이터, 검색 범위, 부분 읽기, 바이너리 미리보기/해석된 레코드, 불완전 아카이브를 구별하세요.
사용자가 선택한 증거와 모델이 선택한 인용의 연결을 뒤에서 기록하면서 실제 읽지 않은 부분을 근거로 승격하지 않는
방법을 설계하세요. 단순 metadata_checked, 반환 내용 hash, 원본 전체 무결성의 차이도 보존하세요.
CAS/중복 방지/버전/정정/철회를 유지하면서 모델이 내부 bookkeeping을 덜 하는 계약을 제시하세요.

Q5. 실행 오류와 의미 오류의 복구
인자 오류, 미지원 형식, 자료 부재, 일시 장애, 실행 중/불확실 실행, 권한 거절, 실제 위험을 분류하세요.
각 상태에서 같은 호출 교정/기존 결과 조회/다른 지원 경로/대기/중단 중 무엇을 선택할 수 있는지 설명하세요.
무한 재시도와 너무 이른 강제 중단을 모두 막아야 합니다. 실패 임계값 증가·반복 경고만을 처방으로 제시하지 마세요.
읽기 전용 반복과 상태 쓰기/외부 효과, 부분 진행과 동일 오류를 구별하고 native 중단/goal 상태를 일치시키세요.
고칠 수 있는 판단 오류는 같은 질문에서 정정할 수 있어야 합니다. 일반적 복구에 대화 삭제를 요구하지 마세요.

Q6. 가설·추론·가정을 허용하는 품질 기준
직접 입증이 부족해도 유력한 설명을 선택하는 기준, 중요한 경쟁 설명을 다루는 기준, 과도한 보류를 막는 기준을 제시하세요.
초안/저장 거절, 작업 중 채택 판단, 최종 전달/완료에 실제 사용된 결론을 구분하세요.
오류의 영향과 실질적인 정정 기회에 따라 계속 관측/정정/중단을 결정하되, 의미 정확성을 필드 개수나 자동 점수로
보장한다고 주장하지 마세요. 가설을 자유롭게 세우면서 없는 관측을 사실로 쓰는 것은 막는 예시를 보여 주세요.
감독자의 선호와 다른 해석, 반론이 남은 결론, 동일 문장의 과거 이력 조회를 새 실패로 취급하지 마세요.

Q7. 문맥·기억·압축·재개
현재 질문/근거/반론/다음 행동과 오래된 상세를 어떻게 구분하고 필요할 때 복원할지 설계하세요.
정정된 결론이 과거 요약으로 되돌아가거나, 명령·실패가 실행 성공으로 요약되지 않아야 합니다.
다른 사건/삭제 대화/과거 사례가 현재 근거에 섞이지 않도록 하면서 장기 작업의 재탐색 비용을 줄이세요.
취소/압축 실패/부분 완료/프로세스 재시작에서 잃지 않아야 할 상태를 정하고 별도 압축 모델 루프가 꼭 필요한지 검토하세요.

Q8. 포렌식 도구와 플러그인·스킬의 실제 전문성
지원하는 자료 형식과 실제 조사 행동을 먼저 확인하고, 필요한 파서·스킬·플러그인을 기능 단위로 제안하세요.
전문성은 경고문이나 필수 양식의 수가 아니라 자료 이해·시간/계정/프로세스/통신의 대조·가설 판별 능력으로 평가하세요.
도구/스킬 검색과 지연 로딩, 목적 중심 인터페이스, 최소 권한, 승인된 통신, 신뢰할 수 없는 자료/스킬의 경계를 설계하세요.
범용 shell을 열어주는 것과 새 파서를 제공하는 것의 위험 차이, 실행 불가능한 증거 읽기 경계를 구체화하세요.
필요한 경우 코드 재사용보다 작은 어댑터나 설계 참고가 나은지 설명하세요.

Q9. 종결·보고·사용자 경험
사용자 질문에 답했는지, 중요한 의심과 누락을 다뤘는지, 남은 검사의 가치가 있는지가 중심이 되게 하세요.
모든 등록 항목의 종료나 자료 수집량이 성공 조건이 되어서는 안 됩니다. 근거 있는 불확실한 종결도 허용하세요.
중요한 가용 검사를 숨긴 최종 완료를 어떻게 구별할지 설명하세요. 판단과 보고가 같은 현재 상태를 보도록 하고,
원문·정정 이력·핵심 한계를 다시 찾기 쉽게 하되 파생 UI 때문에 두 번째 원장을 만들지 마세요.
진행 화면은 현재 행동·실제 진행·오류/대기 원인을 보여 주고 내부 절차를 사용자의 관리 업무로 전가하지 않아야 합니다.

Q10. 엔진·모델·도구·감독 효과의 분리
같은 모델/증거/예산에서 도구 계약과 문맥 변화의 효과를 비교할 작은 행동 평가를 설계하세요.
모델 변경 실험은 별도 승인/별도 기준선의 선택지로만 제시하세요. 이번 검토에서 모델 교체를 실행하지 않습니다.
비용은 전체 입력(캐시 포함), 캐시, 새 입력, 출력, 압축/부가 호출, 시간, 중복 읽기를 구분하세요.
감독 개입으로 회복한 실행과 자율 복구, 같은 사건 재시작과 독립 시험을 구분하세요.
모든 오류를 초기에 정지하는 감독이 실제 회복 능력을 가리고 있지는 않은지도 평가하세요.

7. 반드시 포함할 회귀·행동 평가 시나리오
=======================================
각 시나리오에 사전 상태, 합성 입력, 기대 행동/반환, 관측 위치, 실패 기준을 붙이세요.
코드 계약 검사와 실제 모델 행동 평가를 분리하고, 기대 결과를 특정 정상/침해 문구의 일치로만 정의하지 마세요.

1) 정확한 직접 읽기에서 미션/평가 준비 없이 근거가 있는 현재 답까지 연결.
2) 새 본문/페이지와 같은 본문의 반복을 구별하고 영수증 ID/reason 변동에 흔들리지 않기.
3) 선택한 인용은 정확하지만 주장이 과장된 초안에서 같은 조사 안의 실질적 정정.
4) 불확실한 정황의 독립성·경쟁 설명을 비교한 유력 판단 허용.
5) 일부 검색 0건을 전체 부재로 확대하지 않기.
6) 명령 기록·설정·mtime을 실제 출력·성공·실행 순서로 바꾸지 않기.
7) 정상 잡음이 많은 자료에서 가치가 낮은 재검사를 줄이고 중요한 의심을 추적.
8) 새 반증이 나오면 필요한 질문/범위만 다시 열고 과거 정정 이력 보존.
9) 잘못된 인자 1회 뒤 정확한 피드백으로 수정, 다른 대상의 성공을 실패 대상 복구로 오인하지 않기.
10) 미지원 형식·실제 없음·부분 탐색·일시 장애를 구별한 대안 선택.
11) 읽기 중 타임아웃/취소/불확실 반환 뒤 원장 조회로 중복 실행 방지.
12) 페이지로 나뉜 공백/검색/목록을 전체로 오해하지 않기.
13) 동일 이름 아카이브 멤버·다중 볼륨·오래된 참조·메타데이터 유지 변조의 경계.
14) 바이너리 미리보기를 해석된 레코드나 전체 본문으로 승격하지 않기.
15) 동시 수정 충돌과 중복 요청에서 질문/근거의 안전한 원자적 저장.
16) 변경된 명제/범위에 과거 판단을 자동 승격하지 않기.
17) 압축 후 핵심 근거·반론·정정·실행 실패 보존과 오래된 확신의 부활 방지.
18) 현재 대화·부모/압축 세션·다른 사건·보존 과거 사례의 경계.
19) 한 질문의 차단이 가능한 다른 조사를 막지 않기.
20) 중요한 범위를 다룬 불확실한 종결 허용, 가치가 큰 미검토를 숨긴 완료 거절.
21) native halt·goal pause·실행 유휴·재개 권한의 일치와 사용자 수동 중단 존중.
22) 악의적인 증거/도구 출력/플러그인 지시가 원본 쓰기·실행·외부 전송을 유발하지 않기.
23) 렌더된 보고·현재 질문·정확 출처의 버전 일치와 의미 한계 보존.
24) 감독의 정정 안내가 있었다면 실제 전달/정정 결과를 남기고 자율 성공과 구분.

8. 기대하는 산출물 — Codex가 이어서 구현할 수 있도록
=====================================================
A. 한 페이지 판정: 현재 구조의 장점, 확인된 결함, 아직 입증되지 않은 가설, 유지/제거/교체의 핵심 결정.
B. 프로젝트 비교·체리피킹 근거표: 최신 확인 시점/고정 출처/메커니즘/도입 방식/라이선스/위험/채택 또는 거절 이유.
C. 현재와 목표 아키텍처: 책임·단일 상태 소유자·실행 및 데이터 흐름, 실패/취소/압축 경계가 드러나는 그림.
D. 모델이 실제 보는 인터페이스: 기본 흐름, 필수/선택 입력, 실제 반환과 오류 복구 예제, 현재 대비 줄이는 관리 업무.
E. 레거시 정리표: 파일/함수/도구/스키마별 유지·단순화·통합·제거, 사용처, 호환/마이그레이션 및 삭제 근거.
F. 단계별 구현 지시서: 의존 순서, 수정 위치, 변경 계약, 테스트, 완료 조건, 배포 전제, 롤백.
   첫 단계도 오류 한 문구 수정으로 끝내지 말고 관련 경계를 함께 개선하는 작고 일관된 묶음으로 정의하세요.
G. 회귀·행동 평가 명세: 위 시나리오와 추가 반례, 비용/진행/답의 유용성 지표, 대조 조건과 한계.

I. 남은 결정과 반론: 필요한 사용자 결정만 명시하고, 기본 권고와 이를 뒤집을 증거를 함께 제시하세요.
