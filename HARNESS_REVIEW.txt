자료 범위
=========
이 문서는 공개 코드의 설계·입력 계약을 검토하기 위한 질문서다.
사건 원문, 실제 경로·식별자, 운영 설정·주소·인증정보, 대화·로그는 포함하지 않는다.
아래 경로는 합성이다. 운영 관측의 상세 집계는 별도로 제공하며 공개 코드만으로
실제 사건의 정답이나 제공자의 원시 생성을 검증할 수 있다고 주장하지 않는다.
읽은 코드 / 운영자 관측 / 원인 가설 / 미실행 제안을 구분해 답해 달라.

목표와 유지할 경계
==================
Forsic은 Hermes 위에서 동작하는 포렌식 전문 에이전트다. 스스로 자료를 읽고,
가능한 설명과 반론을 비교하고, 중요한 의심을 추적하며, 근거와 한계가 분명한
답을 만드는 것이 목적이다. 미션·평가 절차를 수행하는 관리 시스템이 목적은 아니다.

- Hermes native loop/goal/session/도구 실행/압축/중단·재개를 유지한다.
- 원본 읽기 전용, 사건 경계, 실제 실행·반환, 정확한 참조와 버전을 보장한다.
- 판단·우선순위·대상 선택·종결 범위는 에이전트가 결정한다.
- 최신 경로/미션/멤버를 몰래 선택하거나 누락 인자를 추정해 채우지 않는다.
- 별도 실행기·판단 장부·자동 검토 모델 루프를 전제로 설계하지 않는다.
- 구조 검사 통과와 의미 정확성, 본문 읽기와 전체 조사 완료를 구별한다.

이 커밋의 변경
==============
1. 기본 흐름을 직접 읽기·검색 → 명시적 근거 선택 → 현재 판단 저장으로 바꿨다.
   미션은 사전 판별 조건을 보존할 필요가 있을 때 선택적으로 쓴다.
2. 읽기 반환에 실제 제시된 보존 필드를 선택하는 C2 citation_ref를 제공한다.
   기존 C1 source 참조와 정확 버전 검증을 유지한다. 참조는 근거 자동 채택이 아니다.
3. forsic_question의 선택적 judgment에서 지지/반대 근거와 추론·가정·한계를 받는다.
   기존 노트 단일 writer로 저장하며 가짜 mission/test/assessment를 만들지 않는다.
4. 선택적 미션 평가는 forsic_assess 한 호출로 받으며 별도 평가 준비 호출을 없앴다.
   구형 질문 생성·사후 미션·평가 준비·보고 도구 4개는 native 목록에서 제거했다.
   이력 호환을 위한 내부 코드와 원장은 보존했다. 노트 도구는 이력 조회용이다.
5. Forsic 도구의 비교 투영을 기존 native 반복 감지에 연결했다.
   영수증 ID·reason 변동과 실제 본문/페이지 변화가 구분되도록 한다.
   비교 정보만 바꾸고 보존 원문이나 모델 반환을 동일하다고 삭제하지 않는다.
6. 일반 이미지 읽기는 필수 path/action/file_path를 가진 직접 입력 도구로 분리했다.
   저장된 미션 참조 실행도 선택 경로로 유지한다. 실패한 읽기의 명시적 재시도는
   정확한 기존 실패·미션·활성 goal 경계를 검사하며 자동 재실행하지 않는다.
7. Forsic TUI 상태 문구와 표시 항목을 정리하고 토큰 생성 속도를 유지했다.
   이는 조사 능력이나 오류 복구의 성공 증거가 아니다.

남은 구체적 검토 대상
====================
forsic_image_files의 native 모델 스키마는 여러 action의 합집합이다.
최상위 required는 path/action이다. archive_read의 file_path/member_index 필수성은
설명에 있지만 선택 action과 결합된 필수 조건으로 노출되지 않는다.
실제 실행 admission은 image_action_contract(action)을 사용해 다음을 검사한다.

  archive_list: path, action, file_path
  archive_read: path, action, file_path, member_index

path/file_path는 빈 문자열이면 거절하고 member_index는 0 이상의 정수여야 한다.
불완전한 입력은 backend_started=false, failure_stage=admission으로 보존한다.
이 실패는 자료 부재나 압축파일 손상이 아니다. 단순히 검증을 약하게 만들지 말아 달라.

합성 유효 입력:
  forsic_image_files({"action":"archive_read","path":"evidence/disk.e01",
    "file_path":"/collected/capture.tar.gz","member_index":7})
합성 실패 입력:
  forsic_image_files({"action":"archive_read","path":""})
  forsic_image_files({"action":"archive_read","path":"evidence/disk.e01",
    "file_path":""})

archive_list는 멤버 번호/이름/종류/크기와 범위를 반환한다. 하지만 모델이 선택한
멤버의 완전한 read call 또는 버전 결속된 읽기 참조를 반환하는 경로는 아직 없다.
모델은 이미지 경로·내부 압축파일 경로·멤버 번호를 다시 조립해야 한다.
반환을 풍부하게 하면 크기도 늘어난다. 별도 준비 단계·미션을 추가하지 않고
이 부담을 줄이는 방법을 검토해 달라.

image_files의 action enum에서는 read/read_bytes를 제거했지만 공통 action 설명에
해당 안내가 남은 부분도 있다. 코드의 표현 불일치와 실제 실패의 인과는 구분해 달라.
path의 minLength가 있어도 실제 생성에서 강제되지 않으면 빈 값은 가능하다.
스키마 개선만으로 모델/제공자의 필드 생성 문제가 모두 해결된다고 단정하지 말아 달라.

관측 경계
=========
진단의 pre_sdk_merged_body는 SDK 호출 직전 구성한 body이며 실제 HTTP 캡처가 아니다.
accumulated_before_repair는 SDK 스트림 누적 후 JSON 복구 전이다.
이 지점의 필드 누락은 복구 이후 유실과 구별할 수 있지만 제공자 원시 생성은 보이지 않는다.
내부 alias는 submitted_tool/submitted_arguments와 canonical 원장 이름을 대조해야 한다.
질문 전용 도구의 평면 입력을 reporting payload로 바꾸는 의도된 변환도 구분해야 한다.

반복 실패 halt와 durable goal paused, 서버 생존과 실제 실행 임대도 따로 확인해야 한다.
같은 도구 성공 뒤 실패 카운터가 리셋되는지, 같은 도구 이름의 여러 action에 대한
카운트가 어떤 교정 기회와 중단을 만드는지 실제 코드에서 검토해 달라.
현재 코드·오프라인 검증을 실제 모델의 자율 복구나 전체 E2E 성공으로 제시하지 않는다.

질문
====
1. 현재 코드에서 확정 가능한 입력/복구 계약 결함과 아직 관측이 부족한 원인을 나눠 달라.
2. 첫 패치 한 가지를 고르고 파일/함수, 모델 입력·반환의 전후, 제거할 중복을 명시해 달라.
3. action별 모델 스키마, 완전한 next_call, 보존 목록+명시적 멤버 참조,
   목적별 얇은 읽기 도구를 호출 수·토큰·안전성·구현량으로 비교해 달라.
4. 참조 방식이면 사건/세션·버전·중복 이름·볼륨·페이지·미완료 목록·변조·부분 읽기를
   어떻게 검증할 것인가? 암묵적인 최신 대상 선택과 정확 복원을 구분해 달라.
5. 기존 반복 감지를 유지하면서 유효한 교정/대안 전환과 같은 실패 반복을 최소 변경으로
   구분할 방법은 무엇인가? 임계값 증가나 경고 추가만을 해결책으로 삼지 말아 달라.
6. 중간 답 저장과 정확한 근거 채택을 구분하면서 별도 의무 절차 없이 현재 판단으로
   이어지게 할 방법은 무엇인가? 숨긴 중요한 공백과 정당한 범위 종결도 구분해 달라.
7. 오프라인 계약 검사에 빠진 행동 평가를 제시하고 모델·입력·예산을 고정한 작은
   비교 실험을 설계해 달라. 미실행 제안을 실제 통과로 표현하지 말아 달라.
8. 유지/삭제/첫 패치/오프라인 검증/운영 재개 조건/실패 시 중단을 순서대로 제시해 달라.

원하는 결과
===========
코드를 직접 읽었다면 정확한 커밋·파일·함수로 근거를 제시하고, 읽지 못했다면 밝혀 달라.
강한 반론과 더 작은 대안을 포함하되 도구·영수증·필수 절차를 계속 늘리지 말아 달라.
운영 수정·재개·모델 변경·전송은 이 질문서의 요청이 아니다. 먼저 검토 결과를 받고 싶다.
