계약의 결함과 중복 입력 부담을 구별하는 것입니다. 코드를 읽을 수 없다면 먼저 밝히고,
읽은 것처럼 답하지 마세요. 정확한 커밋·파일·함수와 함께 다음을 구분해 주세요.
  코드에서 확인한 사실 / 운영자가 전달한 관측 / 원인 가설 / 아직 실행하지 않은 제안
원본 증거, 사건·세션 ID, 대화·도구 반환 원문, 실제 경로, 원격 주소와 자격정보는 제외했습니다.

제공자 원시 생성을 재현할 수는 없습니다. 예제 경로와 ID는 합성입니다.
검토 요청이며 모델 교체·새 모델 시험·새 사건·운영 재개·외부 전송 승인이 아닙니다.

제품 목표와 유지할 경계
=======================
사용자 질문에 답하는 로컬 포렌식 에이전트입니다. 정상으로 설명된 범위는 정리하고, 중요한
의심과 반론은 추적하며, 자료가 부족해도 근거·가정·한계가 추적되는 가장 유력한 판단을 원합니다.
모든 파일 검사, 무한 보류, 근거 없는 확정 어느 것도 목표가 아닙니다.
- 판단·우선순위·검사 선택·종결은 에이전트가 담당합니다. 하네스는 원본 읽기 전용, 사건 경계,
  실제 반환, 정확한 참조/버전, 실행과 평가의 연결을 보장합니다. 구조 검사는 의미 판정이 아닙니다.
- Hermes native loop/goal/session/도구 실행/압축과 기존 사건 원장을 유지합니다. 두 번째 실행기,
  판단 장부, 자동 리뷰 모델 루프를 전제로 설계하지 마세요.
- 미션은 정확한 검사 계획의 저장입니다. 저장이 실행 성공이나 평가 완료는 아닙니다.
- 경로나 최신 미션을 조용히 추정해 누락값을 채우거나 정확 인용·버전 검증을 완화하지 않습니다.
- 현재 실행은 반복 실패 뒤 감독자가 정지했습니다. 후속 관측에서도 새 실행은 없었습니다.
  중요 질문은 active/undetermined, 통신 자료 읽기 미션은 draft, 기존 보고서 4개는 stale입니다.
  전체 조사 성공이나 무개입 E2E 성공을 선언하지 않습니다.

최신 관측: 성공과 실패의 경계
=============================
A. 미션 저장 전 계약 수정
이전 tool_arguments는 여러 도구의 선택 필드 합집합이라 도구별 required/허용 필드를 잃었고
임의 tool_name도 허용했습니다. 지금은 등록된 9개 도구 이름과 각 실제 native 스키마를
이름 있는 tool_arguments.anyOf 분기로 노출합니다. 선택 도구와 인자의 결합은 기존 저장 전
검증이 확인합니다. anyOf만으로 별도 tool_name과의 결합까지 보장한다고 주장하지 않습니다.
실제 session pin과 검증한 후보 스키마의 일치도 확인했습니다.
관련 오프라인 검사 111개, 정상 입력 16개와 보존 실패 입력 5개의 전후 대조를 통과했습니다.
동일 사건 재개 후 처음 4회 모델 응답/도구 반환에서는 미션 저장 → crontab 사본 15행 전체 읽기
→ 정확 source 조회 → 평가 저장까지 오류 없이 진행했고 두 번째 미션도 저장됐습니다.
해당 사본의 국소 관측이며 전체 예약 작업/호스트 정상의 증거는 아닙니다. 재개 안내가 포함된
같은 사건이므로 무개입 E2E나 패치 단독 효과로 해석하지 마세요.

B. 해결되지 않은 실제 실행 문제
두 번째 미션에는 통신 자료의 정확한 file_path와 실행용 next_call이 저장됐습니다. 이후
native 읽기 호출 10회에서 file_path와 mission_id/mission_version이 누락됐습니다.
image_files는 path/action만 필수이고 image_reader.inspect는 file_path 누락 시 '/'를 사용해
IsADirectoryError를 반환했습니다. 실패 인자도 현재 노출 스키마의 필수 필드 검사는 통과합니다.
reason이나 설명에서 경로를 말하는 것과 실제 인자 객체에 넣는 것은 달랐습니다.

합성 예시 — 실제 사건 값 아님:
  도구: forsic_image_files
  next_call.arguments:
    {"path":"/evidence/example.E01","action":"read","file_path":"/capture/network.txt",
     "mission_id":"M-example","mission_version":"exact-saved-version"}
  실패 호출과 같은 구조:
    {"path":"/evidence/example.E01","action":"read","reason":"통신 자료 확인"}
reason으로 경로/미션을 추정하거나 '/'를 목표 파일로 간주하면 안 됩니다.

성공 읽기 1회, 실패 읽기 10회, 검색 1회의 총 12개 이미지 호출을 대조했습니다.
- 보존된 native assistant 인자와 사건 원장의 실행 시작 인자는 전달된 검사 필드에서 일치했습니다.
- 이름 변환 해제와 인자 coercion의 오프라인 재현에서 제공된 필드가 사라지지 않았습니다.
- 제공자 파서 이전 원시 생성은 미관측입니다. 모델 생성/문맥/제공자 파싱 원인은 미분리입니다.
  모델의 “전달 중 경로가 사라졌다”는 설명은 입증되지 않았습니다.
- '/'에서 별도로 한 검색은 82바이트의 불완전 범위에서 0건이었습니다. 목표 파일 부재나
  통신 검사 완료로 바꿔 해석할 수 없습니다.
이 재개의 완료된 모델 응답/도구 반환은 각 16건, 도구 오류 10건, 새 본문/평가 1건이었습니다.
입력 합계 1,484,210토큰 = 캐시 재사용 1,387,996 + 새 입력 96,214; 출력 5,894토큰입니다.
누적 입력은 반복 이력을 포함하며 새 증거량이 아닙니다. 중단된 다음 요청의 미반환 사용량은
제외했습니다. 반복 재개만으로 개선된다는 증거가 없어 감독자가 정지했습니다.

함께 검토할 문제와 기존 수정
============================
1. 범위 종결: 수집 스크립트/계정 이력의 정상적 수집 경위를 시스템 전체 정상으로 넓혔고,
   확보된 목록의 프로세스·통신·시작/예약 작업 본문을 읽거나 낮은 가치로 처분하지 않은 채
   로컬 검사를 소진했다고 종결했습니다. 43개 목록을 44개로 부르는 오류도 있었습니다.
   중요도 누락에 따른 완료 검사 우회는 고쳤고 원래 질문 정의를 유지하며 재개했습니다.
   수집 과정/수집된 상태, 목록/본문 범위를 구분하도록 지침을 보완했지만 의미 정확성은
   미검증입니다. 모든 파일 검사나 특정 정상/침해 결론을 강제할 이유로 삼지 마세요.
2. 입력 오류: outcome enum, gap_id, source/mission 버전, exact_excerpt 범위를 혼동했습니다.
   전용 평면 입력 도구, 실제 스키마, 복사 가능한 citation/next_call, 구체적인 오류 안내를
   제공했습니다. 미션 저장 계약이 개선돼도 다음 실제 호출에서 값이 누락되는 문제는 남았습니다.
3. 압축: 긴 현재 요청이 과거 미리보기 길이 제한을 넘으면 요약 대상이 0개가 되는 native 조건을
   수정했습니다. 요청 원문 재주입, tool pair, 미디어/다중 사용자 보호, 취소/rollback은 유지했습니다.
   실제 압축 1회는 1,414.588초 후 committed, 입력은 123,319→51,133토큰이었습니다.
   이후 자연 압축은 1,163.445초, 101,662→44,906토큰이며 활성 질문/검사 계획이 보존됐습니다.
   운영 복구 관측이지 통제된 효율 비교나 모든 판단의 의미 보존 증명은 아닙니다.
4. 효율화: 모델용 미션/평가 영수증을 줄이고 텍스트와 중복된 Base64만 기본 반환에서 생략했습니다.
   원장 원본과 명시적 조회는 유지합니다. 보존 반환 7건의 읽기 전용 변환은 62,154→36,627바이트였으나
   전체 토큰/지연 절감률은 미측정입니다. native 요약의 중복 작업일지도 줄였고 웹 UI에는 세션 누적
   K/M 토큰을 표시했습니다. 반대로 최신 미션 스키마는 3,438→5,411자로 커졌습니다.

승인 모델은 사설 Ollama qwen3.8-flash-next:iq4_xs입니다. 현재 운영 설정은 context 131,072,

모델 지문·서버 버전·sampling·실효 스키마·압축 조건을 고정한 비교표/홀드아웃 시험은 없습니다.
회귀검사는 구조 계약만 확인하며 일부 모델/압축 응답은 mock입니다. 앞선 검사 개수는 서로
겹치므로 독립 시험 수로 합산하지 마세요. 공개 스냅샷의 회귀 통과도 의미 시험이 아닙니다.
공개 직전 동일 스냅샷에서 제품/배포 검사 213개, native 압축 검사 16개와 test_dashboard.cjs가
통과했습니다. 알려진 대기 문제의 HTTP 검사 1개는 제외했으며 전체 HTTP/API suite를 통과했다는
주장이 아닙니다. Python 검사는 네트워크 연결을 차단했고 실제 모델 호출은 하지 않았습니다.

질문 — 우선순위대로 답해 주세요
===============================
Q1. 실패 원인을 어디까지 좁힐 수 있습니까?
스키마 생성/세션 pin → 요청 조립/직렬화 → 제공자 생성·파싱 → 응답 수용/저장 → 이름/형 변환
→ native dispatch → Case.invoke 경계를 따라가 주세요. 확정 결함과 미확인 원인을 나누고
각 가설을 반증할 관측을 제시해 주세요. 다음 재개 전에 필요한 최소 계측은 무엇입니까?
원문·키를 남기는 전면 디버그 로그 대신 로컬 한정 필드 존재/타입/스키마 지문/호출 결속 등
원인을 분리할 수 있는 가장 작은 계측 범위를 원합니다.

Q2. 계획한 인자를 다시 작성하는 부담을 줄일 가장 작은 방법은 무엇입니까?
“전체 계획 저장 → next_call 복사 → 전체 인자와 미션 ID/version 재생성” 구조를 검토하고
아래 후보의 변경량·위험·native 호환성을 비교해 주세요. 더 작은 대안도 제시해 주세요.
  A. 기존 도구의 action별 입력 계약 및 dispatch 전 검증
  B. 읽기 등 혼동되는 action만 작은 전용 native 도구로 분리
  C. 기존 native handler 안에서 명시적인 불변 미션 참조로 계획 인자를 사용하는 방식
C는 별도 실행기나 최신 미션 자동 선택이 아닙니다. 필요성 자체부터 비판하고 동일 버전/사건/
세션/실행 결속, 재실행·중단·멱등성, 일반 비미션 탐색과의 관계를 설명해 주세요.
모든 탐색에 미션 ID/version을 무조건 요구할 필요가 있는지도 따져 주세요.

Q3. action별 required는 어디에 두어야 합니까?
read/read_bytes/stat/archive_list/archive_read의 file_path와 list/volumes/search의 정당한
기본 범위를 구분해 주세요. anyOf 분기, 도구 선택, native schema sanitizer, 저장 전 검증과
실제 실행 검증의 차이를 확인하고 한 원천에서 계약을 파생할 최소안을 제시해 주세요.
문법적으로 통과하는 실패 인자와 실제 수용 가능한 입력이 왜 다른지, 제공자의 JSON Schema
지원 한계가 있을 때 실행 검증이 무엇을 책임질지 명시해 주세요.

Q4. 같은 오류를 언제 중단하고 어떻게 복구해야 합니까?
reason/operation_id만 바뀌고 유효 검사 인자가 같은 재시도를 기존 native 흐름에서 다룰 방안을
검토해 주세요. 잘못된 입력, 일시적 실패, 느린 정상 작업, 자료 부재를 구별하고 복구/질문별
차단/전체 정지 기준을 제시해 주세요. 사건별 문자열이나 새 감독 모델 루프를 만들지 않으면서
오류를 증거 부재로 바꾸지 않고 호출 낭비를 막는 최소 방안을 원합니다.

Q5. 범위 종결과 실제 조사 품질은 무엇으로 검증합니까?
수집 경위→호스트 정상, 부분 검색 0건→전체 부재, 익숙한 포트→정상, 외부 연결→침해 같은
비약을 따로 평가해야 합니다. 지침, 상태 투영, 모델 해석의 영향을 나눌 작은 합성 비교와
실패 기준을 제시해 주세요. 유력한 해석을 허용하면서 과잉 확정·중요 누락·과도한 보류·불필요한
