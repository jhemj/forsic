# 선제적 스킬 크리에이터

> 상태: Deferred / 설계 문서만 작성. 이번 변경은 작업 중 선제적 스킬 제안·자동 추출·백그라운드 학습을 구현하지 않는다.

## 목적과 제안 판단

분석가가 정정한 절차나 시행착오 끝에 성공한 일반화 가능한 작업을 다음 조사에서도 재사용할 수 있게 한다.
예: 특정 압축 형식에서 정확한 멤버를 선택하고 부분 반환을 이어 읽는 과정을 개선했을 때
“같은 형식의 자료를 다룰 때 재사용할 수 있습니다. 기존 스킬의 변경 초안을 검토하시겠습니까?”라고 제안한다.
사건 결론·계정·IP·실제 경로를 저장하는 기능은 아니다.

제안 근거는 반복 횟수가 아니라 해결한 문제, 성공한 실행 영수증, 적용 조건, 알려진 한계와 기존 스킬 대비 차이다.
다음 분류 중 하나를 선택해야 하며 빈틈을 새 스킬 이름으로 채우지 않는다.

| 분류 | 처리 |
|---|---|
| 기존 스킬의 개선 | 현재 version과 실제 변경 diff를 검토 |
| 새 스킬 | 기존 목록에 같은 목적이 없는지 확인한 뒤 draft |
| 새 도구·adapter가 필요한 기능 | 요구사항으로 남기고 별도 요청을 기다림 |
| 일회성 스크립트 | 해당 작업공간에 보존, 공용 스킬에 승격하지 않음 |
| 사건의 사실·운영 정보 | 사건 노트에 유지, 공용 스킬로 복사하지 않음 |
| 재사용 근거 부족 | 제안 보류, 조사 계속 |

SKILL.md를 생성했다고 없는 실행 기능이 생기지는 않는다. 제안만으로 저장소 제작기나 환경 설치를 시작하지 않는다.

## 질문·초안·쓰기 계약

선택지는 **기존 스킬 개선 / 새 스킬 / 이번만 사용 / 나중에**다.
제안 이유, 일반화할 부분, 현재 스킬의 변경점을 작은 카드로 보여준다.
실제 결정을 기다려야 하는 경우 native `clarify`를 쓴다. 이 도구는 응답을 기다리므로 비동기 알림처럼 쓰지 않는다.
선택적 제안 때문에 현재 조사를 멈추지 않도록 기존 채팅의 일반 안내로 남기고, 사용자 선택 뒤 편집 작업을 시작할 수 있다.

동일 절차·대상 revision으로 만든 제안 fingerprint를 기존 native pending metadata에 남긴다.
거절과 “이 사건에서는 다시 묻지 않기”는 해당 사건 범위에서 보존한다. 횟수 채우기나 반복 재질문을 하지 않는다.
상시 daemon, 매 turn마다 전체 대화를 다시 읽는 별도 LLM, 새 skill-write DB는 추가하지 않는다.

쓰기 상태는 `제안 → 초안 → 검토 대기 → 승인된 쓰기 → 검증 → 명시적 활성화`로 나눈다.
native `tools/skill_manager_tool.py`, `tools/write_approval.py`, pending/diff와 기존 skill lifecycle을 재사용한다.
현재 native 기능이 존재한다는 이유로 이 흐름이 이미 Forsic에 연결됐다고 주장하지 않는다.
구현 전 `skill_manage`의 현재 write gate 설정·우회 가능한 직접 쓰기·실패 반환을 확인해야 한다.

승인은 다음 두 값에 결속한다.

- 사용자가 실제 검토한 draft 내용의 SHA-256.
- 수정 대상 스킬의 원래 ID/version/content revision.

어느 값이라도 바뀌면 기존 승인을 쓰지 않고 새 diff를 제시한다.
“초안을 검토한 뒤 저장”을 약속한 흐름에서는 gate 비활성이나 오류를 직접 쓰기로 대체하지 않는다.
저장 성공과 활성화 성공, 기능 시험 성공은 각각 따로 기록한다.

## 자료 일반화와 버전

계정·사건명·주소·증거 경로·비밀값·개인정보·전체 대화와 증거 로그는 공용 draft에서 제외한다.
명령은 자리표시자, 예시는 재배포 가능한 합성 자료로 바꾼다. 필요한 원문은 원래 사건에 보존한다.
가림만으로 충분하지 않으면 초안을 중단하고 사건별 스크립트로 남긴다.

파일 형식·ID·version·충돌 검증·import·ON/OFF는 `forsic_plugin/extension_hub.py`와
`extension_runtime.py`를 사용한다. 사용 중 버전은 덮어쓰지 않고 새 버전을 만든다.
의존 환경은 `environments.EnvironmentManager`의 기존 불변 manifest와 명시적 선택을 따른다.
제안 승인만으로 환경 기본값이나 다른 사건의 선택을 바꾸지 않는다.

## 비용과 회복

입력은 사용자가 요청한 절차, 선택한 성공/정정 실행 이벤트, 현재 스킬의 필요한 부분으로 제한한다.
전체 이력에 대한 정기 모델 순회, memory/curator/background_review 전역 활성화, 자동 경험 수집은 기본 설계가 아니다.
현재 원장의 영수증·오류 복구 결과를 작은 후보로 읽으며 의미 판단은 기존 에이전트가 수행한다.

| 상황 | 회복 |
|---|---|
| 초안 저장 실패 | 실패 단계와 diff 보존, 성공 표시 금지 |
| 사용자 거절 | 같은 fingerprint 재제안 금지 |
| 세션 종료·취소 | pending 상태 보존, 미승인 파일 활성화 금지 |
| 중복 스킬 | 기존 항목의 차이 검토 또는 제안 폐기 |
| 대상 revision 충돌 | 최신 파일 재조회와 새 diff·승인 |
| 재개 | source/draft/target identity가 일치한 단계만 재사용 |
| 기능 검사 실패 | 초안 유지, 허브의 검증 상태를 실패/미검증으로 표시 |

## 구현 접점과 후속 수용 시험

기존 `forsic_plugin/__init__.py`의 turn 완료/실행 기록은 후보를 선정할 관측 접점이다.
이를 매 turn 자동 모델 호출로 연결하지 않는다. 사용자 명시 요청이나 이미 관측한 의미 있는 정정만 사용한다.
`repository_builder.py`는 **사용자가 요청한** 저장소 adapter 제작 흐름이며 이 기능의 자동 트리거가 아니다.
대시보드 관리의 허브 화면은 승인된 draft의 등록·버전·활성화를 표시할 기존 진입점이다.

후속 구현은 최소 다음 동작으로 검증한다.

1. 제안 이유와 적용 조건이 실제 성공·정정 기록에 연결되고 반복 횟수만으로 품질을 단정하지 않는다.
2. 사용자 답변 전 파일 쓰기·활성화가 없고 gate 오류/직접 호출로 승인 절차를 우회할 수 없다.
3. draft 또는 대상 revision 변경 뒤 이전 승인은 거절되며 새 diff를 검토한다.
4. 실제 사건 값·키·전체 로그가 저장되지 않고 합성 예시만 공유된다.
5. 기존 스킬과 중복을 발견하면 새 항목을 남발하지 않는다.
6. 다음 합성 사건에서 native 목록·본문·참조 조회가 가능하며 OFF 상태와 사건별 버전을 존중한다.
7. 거절·다시 묻지 않기·세션 종료·저장 실패·중복 호출·재개를 재현한다.
8. 제안·편집의 입력/출력/캐시/보조 호출 비용과 원장 증가량을 따로 측정한다.
9. 스킬 저장만으로 도구 구현·조사 정확도 향상·모델 학습을 완료했다고 표시하지 않는다.

## 테넌트 연계 — 계속 Deferred

운영기억·사례 공유가 생겨도 이 기능을 자동 활성화하지 않는다. 기억은 현재 테넌트의 운영 설명이며 공용 절차나
다른 테넌트의 조사 근거로 자동 승격하지 않는다. 향후 후보는 원래 tenant/profile/case와 선택한 실행 영수증에
결속하고, 다른 테넌트의 기억·사례·대화를 모아 일반화하는 기본 권한을 갖지 않는다.

초안의 저장 범위(현재 테넌트 또는 명시적인 공용 배포), 실제 내용 hash와 대상 revision을 사용자에게 함께 보여준다.
공용 export 전에는 사건·조직·경로·주소·비밀값과 운영기억의 적용 범위가 제거됐는지 검토한다. 테넌트 관리 권한이나
기억 저장 승인을 스킬 게시·공유 승인으로 재사용하지 않는다. 기억을 고치거나 제외했다고 이미 게시한 스킬이
자동 정정됐다고 표시하지 않으며 별도 diff와 새 승인을 요구한다.

제작 세션은 기존 관리 격리를 재사용해 조사 대화, MEMORY snapshot, 사례와 원본을 상속하지 않는다. 테넌트 전환,
늦게 도착한 응답, source revision 충돌도 현재 scope로 다시 검증한다. 이번 구현에는 후보 순회·모델 호출·초안
쓰기·자동 활성화·백그라운드 학습을 추가하지 않는다.
