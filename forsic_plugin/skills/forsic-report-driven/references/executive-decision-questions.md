# 경영 질문을 조사 미션으로 연결하기

임원은 호출 횟수·해시·파서보다 회사가 무엇을 보유했고, 어떤 침해·노출이 확인됐고,
어디까지 확인했고 무엇이 아직 불명확한지 알고 싶어 한다. 경영 판단·대응 권고는 사람이 한다.
보고서에 '필요한 결정' 항목이나 대신 결정하는 문구를 넣지 않는다. 아래는 사건에 맞게 선택·추가할 예시이지
강제 검사 목록·고정 점수표가 아니다. 적용하지 않을 때는 실제 질문·범위 이유를 남긴다.

## 먼저 생각할 질문

- 개인정보를 보유했는가? 어떤 종류·시스템·기간까지 확인됐는가? 보유 사실, 접근 흔적,
  외부 전송, 실제 개인정보 유출은 서로 다른 명제다. 파일명·스키마만으로 실제 내용·규모를 확정하지 않는다.
- 최초 침입 경로는 무엇인가? 가장 먼저 확보된 흔적, 유력한 경로와 실제 최초 진입 입증을 구별한다.
  노출된 서비스·취약 버전·로그인 실패만으로 그 경로가 사용됐다고 쓰지 않는다.
- 외부 전송 흔적이 있는가? 연결 시도·세션·송신량·성공·내용을 구별한다.
  인터넷 연결 하나나 도구 이름만으로 유출을 확정하지 않는다. 사설 IP를 외부망으로 단정하지 않는다.
- 영향은 어디까지인가? 대상·계정·개인정보·서비스 중 확인 범위와 가능한 추가 피해를 구분한다.

## 기존 Hermes 루프에서 실행

1. 초기 질문과 자료를 보고 해당 경영 질문을 평범한 문장으로 `forsic_note`에 기록한다.
   예: “고객 개인정보가 이 서버에 있었고 외부로 전송됐는가?”가 너무 넓으면 보유·접근·전송으로 나눈다.
   없는 관측을 채우지 말고 현재 가장 유력한 답과 질적 신뢰도·이유, 실제 evidence_ids, 정상 대안, critical_gaps와 next_checks를 쓴다. 직접 관측과 정황 기반 추론을 구분한다.
2. `forsic_reporting(state)`에서 실제 question refs를 읽는다. `requirement`로
   REQ-CORE-ANSWER의 basis_refs에 임원에게 중요한 question refs를 선택한다.
   REQ-IMPACT는 근거 refs와 업무상 의미·미확인 영향을 rationale로 기록한다.
   섹션 목표는 카탈로그 그대로 유지한다. disposition=satisfied를 '침해 입증'으로 해석하지 않는다.
3. 빈 답을 기술 작업 목록으로 덮지 않는다. 보고서 작성 중에도 공백을 발견하면 `gap`에 분류한다.
   반환 미평가는 evaluate_result, 아직 안 읽은 확보 자료는 read_source, 실제 없는 자료는
   request_external_input, 내부 도구/참조 오류는 repair_internal이다. 원래 질문과 의무를 보존한다.
4. 그 공백에서 `mission` 초안을 기록한다. 어떤 원문·대상·기간을 보며 어떤 관측이면
   설명이 달라지는지, 관측이 없어도 무엇을 말할 수 없는지 명시한다. 이미 얻은 결과는 재사용한다.
   새 수집이 필요하면 기존 지원 도구로만 확인하고 반환 뒤 정확 결과판의 평가 미션으로 연결한다.
   접근 권한·데이터 범위 밖이면 요청을 남기고 멈춘다. 스킬이 권한을 만들지 않는다.
5. 결과를 `assess`하여 현재 답을 갱신하고 다시 gaps를 읽는다. 개인정보 보유가 확인됐다고
   유출 질문까지 해결하지 않는다. 무결과·로그 공백·타임아웃은 '없음'으로 승격하지 않는다.
6. 임원용은 현재 답·확인된 영향·중요 불확실성·남은 조사를 먼저 쓴다. 세부 명령·필드·해시·재현은
   실무자용으로 보낸다. 두 독자 결론·F-ID·핵심 한계는 같다. 중요 공백은 요약에서도 유지한다.

예를 들어 전송 로그가 이미 반환됐지만 평가되지 않았다면 새 패킷 수집부터 하지 않는다.
기존 로그의 대상·송신 방향·기간·내용 판별 가능성을 평가한다. 승인된 백업일 가능성과
개인정보 본문 미확인도 함께 남긴다. 송신 사실만 확인되면 '외부 송신 기록은 있으나 개인정보
전송 여부는 미확인'으로 답하고, 본문 종류나 해당 작업 식별을 확인할 다음 미션을 제안한다.
